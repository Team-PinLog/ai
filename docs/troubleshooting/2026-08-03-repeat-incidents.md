`S15P11A705-293`. 이 문서는 **개별 사고의 해결이 아니라 갈래**를 적는다. 각 건의 처리는
자기 티켓·PR·이슈에 있고 여기에는 **무엇이 반복됐는가**만 남긴다.

세 갈래가 2026-08-03 하루에 각각 서너 번씩 났다. **갈래마다 마지막 사고는 앞선 사고의
대응이 이미 있는 상태에서 났다.** 07-31 의 색인 사고 다섯 건이 같은 모양이었고
(`tools/check_docs_index.py` 머리말), 그때의 결론이 여기서도 반복된다 — 차이는
성실성이 아니라 강제 장치다.

**이 문서 자신이 T70 의 첫 시험이다.** 측정 수치·코드 행 번호·배포 상태 값을 옮기지
않고 좌표만 가리킨다. 값이 필요하면 가리킨 문서를 연다.

## T70 — 원문 대신 사본에서 꺼낸 값

**상태: 대응 확정**(`R-18` 「값 대신 출처」로 승격 · **기계 검사는 없다**)

### 증상

낡은 값이 새 결정의 근거가 된다. **그리고 그 사실이 드러나지 않는다.**

### 무엇이 일어났는가 — 넷

**① 철회된 단정이 그것을 인용하며 되살아난다.** 한 트러블슈팅 문서가 판정 처리량을
단정해 적었다가 다음 날 실측이 뒤집혀 **그 문서 스스로 「틀린 서술이다」로 철회했다.**
오늘 발행한 이슈가 그 형태를 되살렸다 — **근거로 그 문서를 인용하면서.**

철회의 대상을 정확히 적어 둔다. **폐기된 것은 값이 아니라 그 값이 상수라는 단정이다.**
값 자체는 그 시점·그 경로의 관측치로 여전히 유효하다. 둘을 뭉치면 「그 숫자를 쓰면
안 된다」와 「그 숫자를 상수로 쓰면 안 된다」가 구별되지 않는다.

이 건은 **지목 자체가 처음에 틀렸다.** 중앙이 이슈 번호를 잘못 짚었고 「폐기」의 범위도
넓게 잡았다. 정정은 원장의 검증 절에 있다.

> 좌표 — `docs/troubleshooting/2026-07-30-seeding-quota-and-encoding.md` 의 `T27` 과 그
> 정정 블록. 되살린 이슈와 그 정정 코멘트. 중앙 판정의 정정은 `.claude/RECALL-CORRECTIONS.md`
> 의 검증 절.

**같은 값의 사본이 더 있다.** 정정되지 않은 채 남은 이슈 본문이 하나 더 있고, 중앙이
다른 티켓의 계약을 쓰면서 같은 값을 명세 개정의 근거로 다시 인용했다. **하나를 고쳐도
나머지는 자기가 낡았다고 말하지 않는다.**

**② 코드 한 행을 인용하고 다음 행을 놓친다.** 측정 하네스의 머리말이 서비스 코드의 한
행을 인용하며 **「이 필드만 판정 프롬프트에 실린다」**고 적었다. 인용한 행 **바로 다음
행에 다른 필드가 있었다.** 같은 블록이 여러 필드를 한꺼번에 싣는다.

그 오독이 **조건을 가른 설계 근거**였고, 그 위에 선 작업은 **이미 병합됐다.** 같은 표가
하네스 README · 구현 리포트 · PR 본문으로 퍼졌다. 티켓 하나를 닫는 것으로는 정리되지
않는다.

> 좌표 — `tools/preset_desc/variants.py` 머리말과 `tools/preset_desc/README.md`,
> `app/service/keyword_service.py` 의 `cand_dicts`, 구현 리포트
> `docs/implements/2026-08-03-preset-description.md`, `S15P11A705-228` 과 그 PR.

**③ 정정을 적어 두고 원래 문구를 다시 꺼낸다.** 중앙이 원장에 정정을 적어 두고, 나중에
워커 계약을 쓰면서 **원래 티켓 문구를 다시 꺼냈다.** 그 문구는 이미 실측으로 반증된
전제였다. 워커가 원문을 열어 잡았다.

> 좌표 — `.claude/DISPATCH-LOG.md` 의 해당 발급 행. 워커 산출물은 `back` 의 PR.

**④ 계약에 실어 보낸 수치가 여러 번 틀린다.** 중앙이 워커 계약에 넣은 수치가 한 건에서
여러 번 틀렸다 — 무엇이 멈춰 있던 시간, 무엇이 빠진 횟수, 대상의 개수. **전부 워커가
원본을 열어 고쳤다.**

> 좌표 — `.claude/DISPATCH-LOG.md` 의 해당 발급 행과 워커 리포트
> `docs/implements/2026-08-03-dev-deploy-gap.md`.

### 넷의 공통점

**값을 문서에 복사했고, 값은 시점에 묶이는데 문서는 따라가지 않는다.**

그리고 **넷 다 사본을 읽은 사람이 아니라 원문을 연 다른 사람이 잡았다.** 이것이 이
갈래의 핵심이다 — 사본을 읽는 사람은 **확인할 것이 있다는 사실 자체를 모른다.**

### 왜 재조회로 못 막는가

**「확인해야 한다」는 신호가 사본에 없다.** 사본은 자기가 낡았다고 말하지 않는다.

읽는 쪽에 「쓰기 직전 재조회」를 요구하는 규칙은 **이미 있었다.** 그런데도 넷이 났다.
철회를 적어 둔 것도, 정정을 적어 둔 것도 막지 못했다. 읽는 쪽 규칙은 **읽는 사람이
의심할 이유를 가질 때만** 작동하는데, 사본은 그 이유를 주지 않는다.

### 대응

**쓰는 쪽에 규칙을 둔다 — 값을 옮기지 않고 좌표를 가리킨다.** 「쓸 때 조심한다」가
아니라 **애초에 옮기지 않는다**로 적는다.

```
빼는 것      측정 수치 · 현행 상수 · 코드 행 번호 · 배포 상태 값
남기는 것     구조 · 문제 인식 · 설계 방향 · 판정의 성격
써도 되는 것   파일명 · 모듈명 · 티켓 번호 · PR 번호 — 안 바뀌는 좌표다
```

중앙 운영 규칙에서는 이것이 `R-18` 「값 대신 출처」다. 계약을 쓸 때 인용한 수치와 행
번호도 원본을 다시 여는 조항이 함께 붙었다.

> 좌표 — `.claude/CONTROL-PLANE.md` 「값 대신 출처」, `.claude/RATIONALE.md` 의 `R-18`,
> `.claude/CONTRACT.md` 의 계약 작성 조항.

### 검사 가능성

**기계 검사가 없다.** 색인 정합(`tools/check_docs_index.py`)처럼 셀 수 있는 것이 아니다
— 문장이 제안 내용인지 관측값인지는 문자열로 갈리지 않는다.

사람이 묻는 수밖에 없다.

```
이 문장은 제안 내용인가 관측값인가
관측값이면 그 값이 지금도 그런지 누가 보증하는가
보증할 수 없으면 값을 지우고 좌표만 남긴다
```

### 다음 사람에게

**철회를 적는 쪽도 대상을 좁혀 적는다.** 「이 서술은 틀렸다」로 뭉뚱그리면 값과 값의
항상성이 함께 폐기된 것처럼 읽힌다. 무엇이 철회됐는지가 한 문장으로 갈려 있어야 인용하는
쪽이 옳게 인용할 수 있다.

**계약·티켓·이슈는 문서보다 더 위험하다.** 문서는 나중에 고칠 수 있지만 계약은 그것을
읽은 워커가 **이미 그 전제 위에서 작업을 끝낸 뒤**다. ②가 그랬다 — 오독 위에 선 작업이
병합돼 있어 티켓을 닫아도 정리되지 않는다.

## T71 — 반만 덮는 자동화와 조용한 실패

**상태: 부분 해결**(감시 고아는 heartbeat 로 해결 · 배포 자동화 둘은 인프라 소관으로
이슈 기록 · 봉인 값은 성격만 규명)

### 증상

**자동화가 `success` 로 끝나는데 아무것도 안 바뀐다.** 또는 **한 번 지고 나면 다음
기회까지 아무 일도 일어나지 않는다.**

### 무엇이 일어났는가 — 넷

**① 병합 직전 재검사가 경합에 지고, 진 뒤에 스스로 돌아오지 못한다.** 이미지 pin
자동화가 「이 PR 이 pin 하는 태그 == 지금 소스 브랜치 HEAD」를 **병합 직전에 다시
검사한다.** 그 사이 소스 브랜치로 push 가 하나 들어오면 진다.

**검사 자체는 옳다** — 낡은 이미지를 배포하지 않으려는 것이다. **문제는 진 뒤다.** PR 은
낡은 SHA 를 든 채 남고, 갱신 워크플로가 PR 을 다시 밀어야만 재시도된다. 자동화에
재시도가 없다.

**② 그 갱신 워크플로의 cron 이 명목 주기대로 돌지 않는다.** 회차가 **연속으로** 빠졌다.
결과적으로 자동 경로가 한동안 아무것도 하지 않았고, 사람이 수동 실행해 풀었다.

①과 ②는 **같은 이슈에 절을 나눠 기록했다** — ①의 복구가 ②에 걸려 있어 따로 읽으면
「다음 스케줄이 복구한다」로 잘못 읽힌다.

> 좌표 — `infra` 의 이미지 자동 갱신·자동 병합 워크플로 한 쌍과 그 이슈.

**③ 봉인 값이 자동화의 수정 대상 필드 밖이라 갱신되지 않는다.** 프리셋 봉인 값은
배포 값 파일에 있지만, 이미지 갱신 도구가 고치는 필드 목록에 **들어 있지 않다.** 그
도구는 부트스트랩이 켜져 있는지만 확인하고 봉인 값은 읽지 않는다.

**틀려도 실패하는 검사가 없다.** 오늘 실측으로 그 값이 배포를 막지 않는다는 것이
확인됐으나, **「검사가 없다」는 사실 자체는 그대로다.**

> 좌표 — `infra` 의 이미지 갱신 도구와 배포 값 파일, `S15P11A705-61` 과 워커 리포트
> `docs/implements/2026-08-03-dev-deploy-gap.md`.

**④ 감시 스크립트가 세션보다 오래 살아 고아가 된다.** 세션 프로세스가 죽어도 감시
스크립트는 살아남아 계속 폴링하는데, **출력이 어디에도 닿지 않는다.** 폴링은 계속하고
이벤트는 아무도 못 받는다. 고아가 **여럿 쌓여 있었고 아무도 몰랐다.**

**개수로 세는 판정이 원리상 부정확한 것**이 이 건을 오래 숨겼다. 셸의 프로세스 목록은
자기 트리만 보아 살아 있는 것을 0건으로 냈고, 시스템 조회는 순간적인 자식까지 세어
실제 루프보다 훨씬 많은 수를 냈다.

> 좌표 — `.claude/scripts/watch.sh` 의 heartbeat 설계 주석과 `.claude/SESSION-IDENTITY.md`.

### 넷의 공통점

**「성공했다」와 「실제로 반영됐다」가 다르다. 그리고 실패가 조용하다.**

### 성공 판정의 층

네 층을 갈라 물어야 한다. 합치면 앞 층의 성공이 뒤 층의 실패를 가린다.

```
프로세스 생존   돌고 있는가
실행 성공      종료 코드가 0 인가
실제 변경 발생  바뀐 것이 있는가 — 「갱신할 것이 없다」도 success 다
최종 전달 성공  그 변경이 받는 쪽에 닿았는가 — 출력이 아무데도 안 닿아도 프로세스는 산다
```

①은 세 번째 층, ②는 두 번째 층 자체가 일어나지 않은 것, ④는 첫 층만 만족한 것이다.

### 대응

**④는 heartbeat 로 고쳤다.** 스크립트가 자기 상태를 파일로 남기고, 확인 경로가 나이·
출처·중복을 사실대로 보고한다. **판정은 사람이 한다** — 확인 명령은 무엇을 지우면 되는지
까지만 보여주고 죽이지 않는다. 파일 이름에 PID 를 넣은 것이 중복 감지 수단이다.

**①②는 인프라 소관이라 이슈로 기록만 했다.** 우리가 고칠 수 있는 것이 아니다.

**③은 실측으로 성격이 밝혀졌다** — 배포를 막지 않는다. **기록 정합성 문제로 남는다.**
검사를 어느 레포에 둘지는 인프라 소관이 걸려 단독으로 정할 수 없다.

### 남는 것

**cron 이 명목대로 안 도는 것은 그 플랫폼의 성질이다.** 그러므로 **「다음 스케줄이
복구한다」는 전제 자체가 약하다.** ①의 재시도 설계를 ②에 기대어 두면 두 약점이 곱해진다.

## T72 — 방어를 세운 뒤에도 새로 생기는 실사용자 기록 노출

**상태: 미해결 — 대응 미정**(선택지만 정리 · 어느 것도 채택되지 않았다)

> **이 절은 위치와 규모를 적지 않는다.** 실제 경로·질의어·데이터 내용·건수를 적지 않고
> **구조만** 남긴다. 기존 보안 이슈가 「위치는 본문 비공개」로 처리한 선례를 따른다.

### 증상

**방어를 세운 뒤에도 같은 종류의 노출이 새로 생긴다.**

### 무엇이 일어났는가

**① 인지하고 대응을 정했다.** 공개 저장소에 실사용자 기록이 들어 있다는 것을 확인하고
방침을 정했다 — **이력은 두고 앞으로는 훅으로 막는다.** 그 이슈 자신이 위치를 본문에
적지 않는 형태로 발행됐고, 이후 같은 성격의 기록이 그 원칙을 따른다.

**② 결정 한 시간도 안 돼서 같은 종류의 데이터가 새로 커밋됐다.** 측정 산출물이었다.
**재측정 비용을 아끼려고 `.gitignore` 가 명시적으로 예외 처리해 커밋하도록 돼 있었다** —
무시 규칙으로 디렉터리를 덮은 뒤 특정 산출물만 되살리는 형태다.

**③ 훅이 못 막았다.** 훅은 **바깥으로 나가는 발화**를 검사한다 — 이슈·PR·코멘트를
만드는 명령과 티켓을 만드는 도구 호출이다. 그 산출물은 **스크립트가 만들고 사람이
`git add` 했다.** 검사 지점을 한 번도 거치지 않았다.

**커밋 시점에는 검사가 없다.** 저장소에 활성 git 훅이 없고 훅 경로 설정도 없다. CI 에도
같은 대조를 하는 단계가 없다.

**④ 마스킹한 이슈의 코멘트가 가리지 않은 쪽을 안내하고 있었다.** 본문에서 위치를 지운
이슈가, 코멘트에서는 **원자료가 어디에 있는지를 알려 주고 있었다.** 그 안내가 가리키는
것이 ②에서 예외 처리로 커밋된 바로 그 종류의 산출물이다.

**마스킹·예외 처리·훅 사각이 같은 지점에서 만난다.**

### 왜 안 먹었는가

**훅이 덮는 범위와 노출이 일어나는 범위가 다르다.**

```
훅이 덮는 것    사람이 도구를 통해 바깥으로 내보내는 텍스트
덮지 않는 것    스크립트가 만든 산출물 · 그것을 커밋하는 시점
```

그리고 **`.gitignore` 예외가 「커밋하라」고 적극적으로 지시하고 있었다.** 방어의 부재가
아니라 **반대 방향의 지시**가 있었다는 것이 이 건의 성격이다. 훅을 넓혀도 그 지시가
남아 있으면 같은 일이 다시 일어난다.

### 설계 긴장

**둘이 정면으로 부딪힌다.**

```
재측정 비용을 아끼려면    산출물을 커밋해야 한다 — 다시 뜨려면 외부 API 를 다시 부른다
그 산출물이 실데이터를 담으면   커밋이 곧 노출이다
```

산출물을 읽어 결과를 다시 계산하는 도구가 여럿 있다. 그래서 이 긴장은 「지우면 끝」이
아니다.

### 대응 — 미정

**어느 것도 정해지지 않았다.** 선택지만 적는다.

```
산출물을 마스킹본으로 교체    재판정 도구가 깨질 수 있다 — 그 산출물을 읽는 도구가 여럿이다
산출물을 빼고 재측정 비용 감수  외부 API 를 다시 태우는 비용과 재현성 상실을 받는다
검사 범위를 커밋 시점으로 이동  훅이 아니라 커밋 경로에 건다. 사각을 원인 쪽에서 막는다
마스킹 문구에서 경로 안내 제거  **이것만은 즉시 가능하다** — 다른 셋과 독립이다
```

### 다음 사람에게

**「훅을 넣었다」를 방어의 완료로 읽지 않는다.** 훅이 어느 지점을 지나는 것만 보는지
먼저 확인한다 — 편집·커밋·푸시·발화는 서로 다른 지점이고, 하나를 덮는 것이 나머지를
덮지 않는다. 이 갈래는 `T71` 과 같은 모양이다 — **덮은 범위와 사고가 나는 범위가 어긋나
있는데 「대응했다」는 기록만 남는다.**

**예외 규칙은 방어와 반대 방향으로 작동할 수 있다.** 무시 규칙에 예외를 뚫을 때는 그
예외가 무엇을 저장소로 밀어 넣는지를 함께 적는다.
