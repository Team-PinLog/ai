# 판정 프롬프트 A/B 측정 — 죽은 설정 키·라벨 커버리지·조건 노출

`S15P11A705-219`. 구현 리포트는
[판정 프롬프트 규칙](../implements/2026-07-31-judge-prompt-rule.md)에 있다.
이 문서는 **무엇에 걸렸나**만 적는다.

선행 `-210` 의 함정은 [T37~T39](2026-07-31-tau-measurement.md) 에 있고, 이 측정은
그 T39(대조군 없이 재판정 차이를 읽지 마라)를 전제로 설계했다.

## T40 — 죽은 `.env` 키가 「무엇으로 쟀나」를 조용히 바꿔 적게 한다

**상태: 해결됨**(측정 시 벤더를 인자로 고정하고 실제 응답 모델을 회차 파일에 남긴다)

### 증상

`-210` 구현 리포트 §7 의 검증 표가 판정 모델을 `gemini-2.5-flash (thinkingBudget=0)` 로
적고 있다. 그런데 같은 데이터·같은 코드·같은 `.env` 로 판정을 420회 돌린 결과 **답한
모델은 전부 `gpt-4o-mini`** 였다(회차 파일 `models` 필드, 실패 0).

### 원인

`.env` 에 이 줄이 남아 있다.

```
PINLOG_JUDGE_MODEL=gemini-2.5-flash
```

**이 키는 읽히지 않는다.** `S15P11A705-175`(벤더 폴백, 2026-07-30)가
`PINLOG_JUDGE_CHAIN` 으로 대체했고 `.env.example:53` 이 "옛 키는 이제 무시된다"라고
명시한다. `.env` 에 `PINLOG_JUDGE_CHAIN` 이 없으므로 `config.py` 의 기본 체인이 쓰이고,
그 1순위가 `openai:gpt-4o-mini` 다(`-176` 실측으로 정한 순서 — 100%·0.91s).

`.env` 를 열어 「판정 모델이 무엇인가」를 확인하면 **있지도 않은 설정을 읽고 확신하게
된다.** 값이 그럴듯해서(실제로 체인 2순위다) 어긋남이 드러나지 않는다.

키 개명 자체는 이미 알려져 있었다 — `-96·-77` 감사가 "전달본이 낡았다"로 남겼고, 배포
봉인 대상이 아니라 **영향 범위를 「로컬 `.env` 뿐」으로 판단하고 넘겼다.** 그 판단이
맞았다. 다만 로컬 `.env` 가 곧 **측정 환경**이라는 것이 계산에 없었다. 배포는 멀쩡한데
리포트의 조건 표가 틀린다.

### 처방

측정 도구는 설정에서 벤더를 **읽지 말고 인자로 받는다.** 그리고 읽은 값이 아니라
**답한 값**을 남긴다.

```python
run.py --chain openai:gpt-4o-mini      # 조건이지 환경이 아니다
rec["models"] = {result.model: n}      # JudgeResult.model — 실제로 답한 모델
```

`.env` 를 보고 조건 표를 쓰지 않는다. 폴백이 있는 한 **설정 1순위와 답한 모델은 언제든
갈라진다**(`llm_client` 도크스트링이 같은 이유로 `JudgeResult.model` 을 저장에 우선한다).

`.env` 의 죽은 줄은 이 티켓에서 지우지 않았다 — 측정 worktree 의 사본이고, 원본은
개인 환경 파일이라 레포가 소유하지 않는다. **`.env.example` 은 이미 옳다.**

## T41 — 라벨은 현행 판정만 덮는다. 재판정하면 표 밖으로 나간다

**상태: 해결됨**(`labels_extra.yaml` 로 넓히고, 남는 것은 `unlabeled` 로 따로 센다)

### 증상

`tau_grid/score.py` 를 그대로 쓰려 했으나 재판정 결과에는 못 쓴다. 돌리면 멈춘다.

```
[FAIL] 판정에 없는 라벨 …건
라벨과 판정이 어긋났다. 재지 않고 멈춘다.
```

### 원인

`tau_grid/labels.yaml` 은 **현행 τ=0.30 판정이 낸 83행에 대한** 라벨이다. τ 스윕에서는
그것으로 충분했다 — τ 를 올리면 후보가 **빠지기만** 하므로 새 행이 생기지 않는다.

프롬프트는 다르다. 판정을 실제로 다시 부르므로 **없던 조합이 생긴다.** A·B·C 를 5회씩
돌린 결과 라벨 밖 행이 24종 나왔고, 그중에는 현행 판정이 **0행이던 Context** 에 넷이
붙은 경우도 있었다(`286` — 본문이 맛 불평뿐인 글에 `ALONE`·`QUIET`·`LIVELY`·`TRENDY`).

**그 행들을 빼고 세면 조건 비교가 기운다.** 개정 프롬프트가 새로 고른 것이 전부 없는
셈이 되기 때문이다. 「라벨이 없으니 못 센다」와 「세었더니 0이다」는 전혀 다른데
집계표에서는 똑같이 안 보인다.

### 처방

원본은 **한 줄도 고치지 않는다** — 고치면 `-210` 의 수치와 비교가 끊긴다. 별도 파일로
커버리지만 넓히고, 기준은 원본 머리말 그대로 쓴다.

```
tools/prompt_ab/labels_extra.yaml    재판정에서 나온 24행
score_ab.py                          그래도 남는 것은 unlabeled 로 세고
                                     fit·unfit 양극단으로 돌려 결론이 뒤집히는지 본다
```

라벨을 넓힐 때 **같은 본문을 가진 `context_id` 쌍**(`-210` §4.1 의 5쌍)에는 같은 판정을
준다. 한쪽만 다르게 붙으면 그 차이가 조건 효과로 잘못 읽힌다.

## T42 — 조건을 보고 라벨을 붙이면 라벨이 결론을 따라간다

**상태: 해결됨**(덤프에서 조건·회차를 뺀다)

### 증상

증상이 없다. **그것이 이 항목을 남기는 이유다** — 어긋난 티가 어디에도 나지 않고,
집계는 정상으로 돌며, 개선 폭만 부풀어 나온다.

### 원인

T41 을 처리하려면 라벨 밖 행에 사람이 라벨을 붙여야 한다. 그 목록을 뽑을 때 **어느
조건이 고른 행인지 함께 보이면** 판정이 기운다. 개정안이 새로 고른 것에는 「이건 볼
만하다」로, 현행만 고른 것에는 「역시 오분류」로 붙게 된다. 두 방향이 같은 쪽으로
작용해 **개정안이 이긴다는 결론이 라벨 단계에서 이미 만들어진다.**

라벨이 결론보다 먼저 있어야 하는데 순서가 뒤집힌다.

### 처방

덤프에서 조건과 회차 수를 **빼고** 합집합만 `(context, code)` 순으로 낸다.

```bash
python tools/prompt_ab/score_ab.py --dump-unlabeled
```

본문과 프리셋 `description` 만 보고 붙인다. 그래도 남는 한계가 있고 숨기지 않는다 —
**라벨을 붙인 사람이 개정 프롬프트를 설계한 사람이기도 하다.** 「어느 쪽이 골랐나」는
가렸지만 「개정안이 노린 유형이 무엇인가」는 이미 알고 있다. 그 사실을
`labels_extra.yaml` 머리말에 적어 두었다.

## T43 — 사전 기준을 통과하지 못했을 때 자를 바꾸고 싶어진다

**상태: 해결됨**(두 기준을 함께 내고, 어느 쪽이 통과했는지 밝힌다)

### 증상

조건 C 가 오분류를 평균 2.60행 줄였는데 **사전에 정한 「두 조건의 관측 범위가 겹치지
않을 것」을 통과하지 못했다**(A 9~14 · C 6~12). 여기서 자연스럽게 드는 생각이 셋이고
셋 다 결론을 결과에 맞추는 길이다.

```
기준을 「평균이 개선되면 채택」으로 낮춘다
회차를 하나씩 더 돌려 범위가 갈릴 때까지 본다
p 값을 새로 계산해 그쪽만 보고한다
```

### 원인

「범위 비중첩」은 회차 5개라는 제약에서 나온 보수적인 자다. 표본이 늘면 극단값도 늘어
**오히려 통과하기 어려워진다** — n 이 커질수록 좋아져야 할 기준이 반대로 움직인다.
그래서 표본을 늘리면 자를 바꿔야 하는데, 그 교체가 **결과를 본 뒤에** 일어난다는 것이
문제다.

### 처방

자를 바꾸는 것 자체는 정당하다. 바꾸는 **시점과 방식**을 고정한다.

```
표본을 늘린다      A·C 를 10회씩. 조건을 바꾸지 않고 같은 하네스로만 더 돌린다
자를 더한다        순열검정(전수, n=10+10 이면 184,756 가지). 가정을 쓰지 않는다
앞의 자를 지우지 않는다   범위 비중첩 결과를 그대로 함께 낸다
```

`score_ab.py` 가 둘을 나란히 찍는다. **나중에 더한 자가 통과했다고 앞의 자를 무르면
그것은 기준을 결과에 맞춘 것이다.**

```
[사전 기준] 범위가 분리되는가    …
[보강 기준] 순열검정 p<0.05      …
```

효과 없음(B)은 추가로 재지 않았다 — 평균 차이가 0.6행이라 표본을 늘려 갈릴 값이
아니고, 그 판단도 **더 재기 전에** 내려 두었다.

## T44 — DB 에 저장된 판정 1회분의 분포를 신호로 읽으면 안 된다

**상태: 해결됨**(같은 조건으로 한 번 더 받아 대조한다)

### 증상

`ai.context_keyword.confidence` 를 라벨별로 갈랐더니 **유사도가 못 한 분리가 나왔다.**

```
fit      n=63  min 0.70   ← 정상 판정은 0.70 아래로 안 내려간다
unfit    n=10  min 0.30

하한 0.70 을 두면   unfit 4건 제거 · fit 유실 0 · 교환비 0.00
```

`-210` 이 τ 에서 어느 값으로도 교환비 1.22 밖에 못 얻은 것과 비교하면 압도적이라,
그대로 「confidence 필터가 유망하다」를 후속으로 올릴 뻔했다.

### 원인

**그 값은 판정 1회의 산물이다.** DB 에 있는 것은 시딩 때 한 번 돌린 결과이고, 여러 번
돌려 안정된 값이 아니다. 같은 조건으로 42건을 한 번 더 판정해 받아 보면 그림이 사라진다.

```
fit      n=62  min 0.60
unfit    n=8   min 0.60

하한 0.70 을 두면   unfit 1건 제거 · fit 유실 2 — 분리가 없다
```

`fit` 의 최솟값이 0.70 이던 것이 0.60 으로 내려앉으면서 겹친다. **판정이 내는 것은
선택뿐 아니라 confidence 도 비결정적이다.** T39 는 「어떤 키워드를 골랐나」가 흔들리는
것을 봤고, 이것은 「얼마나 확신하나」도 같이 흔들린다는 것이다.

DB 조회는 GMS 를 부르지 않아 비용이 0 이다. 그래서 **여러 번 볼 생각을 안 하게 된다** —
싼 것이 함정이다.

### 처방

저장된 판정에서 어떤 분포·문턱·상관을 발견하면, **후속으로 올리기 전에 같은 조건으로
한 번 더 받아 대조한다.** 42건이면 판정 42회·70초다.

```bash
python tools/prompt_ab/run.py --variant A --reps 1 --start-rep 11 --outdir .prompt_ab/probe
```

`--outdir` 를 나누는 것이 중요하다. 확인용 회차를 본실험 디렉터리에 두면 집계 n 이
바뀌어 이미 낸 결론이 흔들린다.

회차 파일에 `confidences` 를 남기게 해 두었다 — **다시 부르지 않으면 얻을 수 없는 값**
이고, 후속이 재측정 없이 회차 반복분을 볼 수 있다.
