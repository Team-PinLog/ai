## T68 — 임베딩 API 는 **같은 배치 구성으로도** 결정적이지 않다

**상태: 해결됨**(검증 문턱을 실측에 맞췄고, `base2` 조건으로 흔들림을 상시 관측한다)

### 증상

이 티켓의 하네스는 조건마다 프리셋 27개를 다시 임베딩한다. `base` 조건은 시드 yaml
그대로이므로 **DB 에 적재된 벡터와 같아야 한다** — 같지 않으면 하네스의 임베딩 경로가
부트스트랩과 어긋난 것이고 조건 비교 전체가 무효다. 그래서 코사인을 대조하고 `0.9999`
미만이면 멈추게 두었다.

첫 실행이 멈췄다.

```
base 검증 — DB 적재 벡터와의 코사인 최솟값 0.999279 (QUICK_STOP)
```

`0.9993` 은 float32 저장 손실(`~1e-7`)보다 네 자리 크다. **텍스트가 다른가, 경로가
다른가**가 유일하게 그럴듯한 설명으로 보인다.

### 진단이 어긋난 경로

셋을 순서대로 봤고 앞의 둘이 전부 「같다」로 나왔다.

```
① 임베딩 입력 텍스트가 DB 와 다른가        27개 전부 한 글자까지 같다
② 같은 텍스트를 단건으로 다시 뜨면 다른가   DB 와 코사인 1.000000 — 오히려 같다
③ 같은 배치 27건을 두 번 떠서 서로 대조     **갈린다**
```

②가 결정적으로 오해를 부른다. 단건으로 뜬 `QUICK_STOP` 은 DB 와 정확히 `1.000000`
이었다. 여기서 멈추면 「배치로 부를 때만 어긋난다 → 배치 경로에 결함이 있다」로 간다.

③이 답이었다.

```
                    같은 배치 2회끼리        1회분 대 DB 적재분
VIEW_GOOD              0.999393                0.999393
QUICK_STOP             1.000000                0.999279
WITH_KIDS              0.999981                0.999981
나머지 24개             1.000000                1.000000
```

**두 열의 크기가 같고, 어느 항목이 흔들리는지도 회차마다 다르다.** DB 적재분이 다른
것이 아니라 **매번 다르다.**

### 원인

임베딩 API 응답이 결정적이지 않다. 배치 구성·순서·텍스트가 전부 같아도 같은 값이
돌아오지 않는다.

**`T42` 가 이 전제를 반대로 적어 두었다.**

> `-191` 이 「임베딩이 결정적이라 실패 2건의 유사도가 소수 넷째 자리까지 일치한다」고
> 적은 것은 **같은 배치 구성으로 다시 돌렸을 때**의 이야기다.

`T42` 는 배치 구성이 **바뀌었을 때** 흔들리는 것을 관측하고 그 조건을 원인으로 지목했다.
관측 자체는 맞지만 조건이 필요조건이 아니다 — 배치 구성을 고정해도 흔들린다.

### 흔들림의 크기와 그것이 무엇을 잡아먹는가

`base` 와 `base2`(글자 하나까지 같은 조건)의 `(Context, Preset)` 유사도 1,134쌍을 대조했다.

```
|Δsim|   최대 0.004413 · 중앙 0.000013
rank     43쌍에서 다르다
후보 집합 τ=0.30·k=10 에서 **42건 전부 같다**
```

마지막 줄이 이 티켓을 구했다. 흔들림이 절단선을 넘지 않으므로 조건 D·E·DE 의 후보
변화는 전부 개정의 몫이다. **넘었다면 이 티켓의 모든 수치가 임베딩 운과 섞였을 것이다.**

### 처방

```
검증 문턱을 0.999 로     텍스트가 실제로 다르면 코사인이 0.9 대로 떨어지므로
                         「경로 어긋남」은 이 문턱으로도 잡힌다
base2 를 상시 조건으로   흔들림을 매 측정에서 다시 재고, 후보 집합이 갈리기
                         시작하면 그때 결론을 보류한다
```

### 다음 사람에게

**`10⁻³` 규모 차이로 채택을 가르지 않는다.** `T42` 가 `10⁻⁴` 로 적은 것을 한 자리
올려야 한다 — 실측 최댓값이 `0.0044` 다.

`-210` 의 τ 격자가 `0.01` 간격이다. 그 안에서 `0.0044` 가 흔들리면 **인접한 두 τ 값의
구분은 신뢰할 수 없다.** `-210` 이 「0.34 와 0.35 의 이득이 같다」고 적은 것은 그래서
운이 아니라 구조다. τ 를 다시 정할 일이 있으면 격자를 `0.01` 보다 촘촘하게 두지 않는다.

임베딩 결과를 커밋해 둔 `.search/matrix.json`(`-215`)의 근거도 이것이다. 다시 뜨면
다른 값이 나오므로 **문서에 적힌 수치를 재현하려면 그때의 행렬이 있어야 한다.**

## T69 — τ 격자의 「fit 유실」이 rank 로 밀려난 행을 세지 않는다

**상태: 해결됨**(별도 집계로 갈라 세고, 리포트는 두 값을 함께 낸다)

### 증상

`tools/tau_grid/score.py` 를 개정 조건(`DE`)의 행렬로 돌렸더니 앞뒤가 안 맞는다.

```
라벨 분포     fit 의 최솟값 0.2554
τ 격자        τ=0.300 에서 fit 유실 **0**
```

`0.2554` 는 `0.30` 아래다. τ=0.30 에서 잘려야 하는데 유실이 0 으로 잡힌다.

### 원인

`score.py` 의 격자 루프가 `rank <= k` 를 먼저 건다.

```python
in_k = [x for x in c["candidates"] if x["rank"] <= k]   # ← rank 11 이상은 아예 안 들어온다
for x in in_k:
    if not x["selected"]: continue
    ...
```

`rank > K` 로 밀려난 행은 루프에 들어오지 않으므로 **어느 칸에도 세어지지 않는다.**
`label_distribution` 은 rank 를 안 보고 `selected` 전부를 세므로 `0.2554` 를 찍는다.
두 함수가 다른 모집단을 보고 있다.

**τ 만 조건일 때는 무해했다.** `-210` 은 임베딩이 고정이라 rank 가 안 변했고, 밀려나는
행 자체가 없었다. 이 티켓은 임베딩을 바꾸므로 rank 가 변한다 — 같은 코드가 조건이
달라지자 조용히 틀린 값을 낸다.

### 실제로 얼마나 빠졌나

현행 판정 83행 중 **후보(rank≤10 ∧ sim≥0.30)에서 빠진 행**을 따로 셌다.

| 조건 | 빠진 행 | fit | unfit | unclear |
|---|---|---|---|---|
| base · base2 | 0 | 0 | 0 | 0 |
| D | 4 | 3 | 1 | 0 |
| E | 2 | 0 | **2** | 0 |
| DE | 5 | 2 | **3** | 0 |

`score.py` 의 τ=0.30 행은 `DE` 에서 「unfit 2 제거 · fit 유실 0」이라고 낸다. 실제로는
**unfit 3 · fit 2** 다. 한쪽만 읽으면 교환비가 `0.00` 으로 보이는데 실제로는 `0.67` 이다.

### 처방

`score.py` 를 고치지 않았다. 그 파일은 `-210` 의 수치를 재현하는 기준점이고, 지금
고치면 세 티켓의 표가 어느 판으로 계산된 것인지 갈린다. 대신 **밀려난 행을 따로 세어
리포트에 나란히 낸다.**

### 다음 사람에게

`score.py`·`sweep.py` 를 **임베딩이 바뀐 행렬에** 댈 때는 이 값을 반드시 함께 낸다.
τ 만 바꾸는 측정이면 필요 없다 — 그때는 rank 가 고정이라 밀려나는 행이 없다.

고칠 거라면 `in_k` 필터를 없애고 「rank 로 빠짐」을 τ 유실과 **다른 칸**으로 세는
쪽이다. 같은 칸에 합치면 「τ 를 올려서 잃었다」와 「다른 프리셋이 밀어내서 잃었다」가
구분되지 않는다.
